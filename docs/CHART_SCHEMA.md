# Strategy chart format

Every file in `strategy_charts/` describes one preflop decision node: a seat, a
situation, and an action for each of the 169 starting hands.

The format is enforced by `logic/chart_schema.py`, which runs at app startup, in
`make validate-charts`, and in CI. A chart that does not validate is a build
failure — it is not silently tolerated.

## File layout

The filename (without `.json`) is the chart key, and must equal
`metadata.chart_id`:

```
cash_6max_100bb_BTN_RFI.json   ->  chart_id "cash_6max_100bb_BTN_RFI"
```

The convention is `{game_type}_{table_size}max_{stack_depth}bb_{hero}_{situation}[_vs_{villain}]`.
Nothing parses the filename, but staying consistent keeps the directory readable.

## Document

```json
{
  "metadata": {
    "chart_id": "cash_6max_100bb_BTN_RFI",
    "description": "6-Max Cash Game, 100bb deep. Hero is on the Button and it has folded to them.",
    "game_type": "cash",
    "table_size": 6,
    "stack_depth": 100,
    "hero_position": "BTN",
    "situation": "RFI",
    "sizings": { "open_bb": 2.5 },
    "explanations": {
      "RAISE": "Why this chart raises.",
      "FOLD": "Why this chart folds."
    }
  },
  "actions": {
    "RAISE": ["AA", "KK", "AKs"],
    "FOLD":  ["72o", "32o"]
  }
}
```

### `metadata` — required keys

| Key | Type | Notes |
|---|---|---|
| `chart_id` | string | Must equal the filename stem. |
| `description` | string | Shown in Study mode. Describe the node, including the sizes it assumes. |
| `game_type` | `"cash"` \| `"mtt"` | |
| `table_size` | integer | Positive. |
| `stack_depth` | integer | Effective stack in bb. |
| `hero_position` | `UTG` \| `MP` \| `CO` \| `BTN` \| `SB` \| `BB` | |
| `situation` | see below | |
| `explanations` | object | One entry per action the chart actually uses. |

### `metadata` — situational keys

| `situation` | Meaning | Also required |
|---|---|---|
| `RFI` | Folded to hero | — |
| `vs_RFI` | Hero faces an open — fold, call, or 3-bet | `villain_position` |
| `vs_3Bet` | Hero opened, villain 3-bet | `villain_position` |
| `vs_4Bet` | Villain opened, hero 3-bet, villain 4-bet | `villain_position` |
| `vs_5Bet` | Hero opened, villain 3-bet, hero 4-bet, villain jammed | `villain_position` |
| `squeeze` | Hero faces an open and a cold call | `opener_position`, `caller_position` |

A villain seat may not be the same as `hero_position`.

`vs_4Bet` and `vs_5Bet` are different nodes, and position order decides which
one a spot can be. Hero can only be *facing* a 4-bet if hero 3-bet, which means
hero acts after the opener; if hero acts first, hero opened and the big raise
coming back at them is a 5-bet. Five charts were originally labelled `vs_4Bet`
while describing a 5-bet spot — their own explanations said "5-bet all-in" —
and were relabelled in phase 1.

> There used to be a separate `3Bet` situation describing the same decision as
> `vs_RFI`, which meant two charts per spot with conflicting answers on up to 34
> of 169 hands. Phase 1 removed it: `vs_RFI` covers the whole decision and its
> RAISE branch *is* the 3-bet. A chart using `3Bet` is now rejected.

### `metadata.source` — provenance

Where the ranges came from. Charts generated by `scripts/author_chart.py` get
this automatically:

```json
"source": {
  "type": "authored",
  "detail": "Hand-authored from standard 6-max 100bb preflop theory. NOT solver output.",
  "date": "2026-10-18",
  "spec": { "RAISE": "22+, ATs+, ...", "DEFEND": "..." }
}
```

`spec` is the range notation the chart was generated from, so the 169-hand lists
carry their own derivation and a range can be reviewed as one line. Be honest in
`type`: `authored` ranges are reasonable reference ranges, not an equilibrium.

### `metadata.sizings` — required

Bet sizes in bb that the ranges were built for: `open_bb`, `3bet_bb`, `4bet_bb`,
`5bet_bb`, `call_bb`.

`logic/nodes.py` builds the spot from these — who acted, for how much, what is
in the pot and what hero has to call. Get them wrong and the user is shown pot
odds that do not match the range they are being tested on, which is exactly
what happened before: every open was hardcoded to 3.0bb regardless of the chart.

Only the keys a situation needs are used. A chart may omit the rest, but what it
does declare must be positive. Anything missing falls back to
`logic.nodes.DEFAULT_SIZINGS`.

### `actions`

An object keyed by `FOLD`, `CALL`, `RAISE`, each a list of hands in canonical
notation:

- pairs: `AA` … `22`
- suited: high rank first, `s` suffix — `AKs`, not `KAs`
- offsuit: high rank first, `o` suffix — `AKo`

All 169 hands must appear **exactly once across the whole document**. A hand
listed under two actions used to be resolved silently by dict ordering; it is
now a `duplicate-hand` error.

Every action key present must have an entry in `metadata.explanations`.

#### Formatting convention

Hands are grouped one rank family per line, strongest first. This is not
enforced, but it keeps diffs reviewable — a one-hand change should be a one-line
diff:

```json
"RAISE": [
  "AA", "KK", "QQ", "JJ",
  "AKs", "AQs", "AJs",
  "KQs", "KJs",
  "AKo"
]
```

Do not reformat a chart with `json.dump`; it flattens these groups and turns a
one-line change into a 200-line diff.

## Stack depth

`metadata.stack_depth` is a real dimension, not a constant. The chart set holds
100bb and 40bb, and every cross-chart rule keys on it: two charts for the same
seat at different depths are different nodes, and a 40bb opening range is not
the range hero holds at a 100bb node.

Shallower is not simply tighter. At 40bb the `vs_5Bet` node does not exist at
all — a 4-bet is committing, so there is no decision after it — and the
`vs_3Bet` nodes become jam-or-fold. Ranges tighten at the bottom, where the
implied-odds hands live, rather than uniformly.

`/api/options` reports the depths actually present, so the setup screen cannot
offer one the chart set does not cover.

## `mixes` — hands the chart plays two ways

Optional, and generated rather than hand-written:

```json
"mixes": {
  "76s": ["RAISE", "FOLD"],
  "75s": ["FOLD", "RAISE"]
}
```

`actions` assigns one action per hand, which states a hard line where real
preflop strategy has a gradient. About a quarter of reachable deals sit on such
a line — 30% in the Big Blind defending spots. Scoring those as a single right
answer marks a legitimate action wrong and docks the user, which over a session
trains the mixed action out of them.

Each entry lists the actions the trainer accepts. **The chart's own action must
come first**, so it remains the primary recommendation; the rest are
alternatives that score as correct and are reported as a close decision rather
than a mistake.

Regenerate after any change to `actions`:

```bash
python scripts/author_chart.py chart_sources/cash_6max_100bb.json   # writes actions
python scripts/derive_mixes.py                                      # then mixes
python scripts/derive_mixes.py --check                              # CI: is it stale?
```

The order matters — `author_chart.py` rewrites the file and would drop a stale
block. `tests/test_mixes.py` fails if the committed mixes do not match the
actions.

### What the derivation does and does not claim

It finds which hands are **close**, not how often to take each line. A hand is
close when the hand immediately next to it in the range matrix is played
differently: 76s is marginal precisely when 75s folds and 87s raises. That is
structural and derivable. Real mixing *frequencies* need a solver, and are not
invented here.

Three guards keep it from saying something false, each with a test:

| Guard | Why |
|---|---|
| At most one alternative | Accepting all three actions leaves no wrong answer. A hand pulled two ways keeps the chart's single answer. |
| Reachable hands only | Hero cannot hold JJ facing a 5-bet they never 4-bet it with. |
| Action groups of 3+ | In a two-hand group every member is an edge. With a raising range of `{AA, KK}`, KK touches a calling hand — but calling KK facing a jam is a mistake, not a close decision. |

When solver output arrives, the same field can carry real frequencies without
changing how anything else reads it.

## Cross-chart rules

Checked by `validate_chart_set`:

- **`duplicate-node`** — no two charts may model the same decision.
- **`unreachable-continue`** — every hand hero continues with must be a hand
  hero could actually be holding at that node. Hero cannot be facing a 3-bet
  with a hand they never opened. The reference range depends on how hero got
  there:

  | Situation | Hero got here by | Reference range |
  |---|---|---|
  | `vs_3Bet` | opening | RAISE branch of hero's `RFI` chart |
  | `vs_4Bet` | 3-betting | RAISE branch of hero's `vs_RFI` chart vs that villain |
  | `vs_5Bet` | opening, then 4-betting | RAISE branch of hero's `vs_3Bet` chart vs that villain |

- **`imprecise-prior-range`** / **`no-prior-range`** — warnings, not errors. The
  chart that would define hero's range at this node does not exist, so the
  trainer falls back to a looser one (or the whole deck) and will deal hands
  hero would not actually hold there. Adding the missing chart clears it.

The same definition drives the scenario sampler, so the validator and the
trainer cannot disagree about what hero can be holding — see
`chart_schema.prior_range_keys`.

## Running the validator

```bash
make validate-charts              # errors fail; known issues suppressed
python scripts/validate_charts.py -v            # list every chart behind a warning
python scripts/validate_charts.py --strict      # warnings fail too
python scripts/validate_charts.py --no-baseline # show known issues as failures
```

At runtime the same checks run when `StrategyManager` loads. Set
`CHART_VALIDATION=strict` to refuse to start when any chart fails.

## The known-issues baseline

`CHART_KNOWN_ISSUES.json` lists errors that are real, understood, and scheduled
for a later phase. They do not fail CI; anything not listed does.

The baseline is self-cleaning: if an entry stops firing — because the chart was
fixed — the validator fails with `stale baseline entries`. Fixing a chart
therefore forces its entry to be deleted in the same change.

Adding an entry requires a `reason` and a `resolved_by` phase. It is a scheduling
tool, not a way to make a problem go away.

## Authoring a chart

Charts in `chart_sources/` are written as range specs and generated:

```bash
python scripts/author_chart.py chart_sources/cash_6max_100bb.json
python scripts/author_chart.py chart_sources/cash_6max_100bb.json --dry-run
```

A spec gives `RAISE` and either `CALL` or `DEFEND`. `DEFEND` is the whole
continuing range, and the calling range is derived as `DEFEND - RAISE` — which
is how the decision is actually reasoned about, and avoids the carve-out
mistakes that come from restating a range minus its raises. Anything unnamed
becomes FOLD, so a generated chart always covers all 169 hands exactly once.

The generator refuses to write a chart that fails validation, and refuses a
`RAISE` range that is not contained in `DEFEND`.

Range notation is documented in `logic/range_spec.py`. Note the conventional `+`
behaviour: `ATs+` walks the kicker up (ATs, AJs, AQs, AKs) while `54s+` keeps the
gap and walks the whole hand up (54s, 65s, 76s … AKs).
